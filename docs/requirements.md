# cpa-workbuddy 需求

> 唯一需求正文。R1–R4 与五项问答共同构成首版范围；业务实现状态见 [14 片任务](tasks/workbuddy-plugin.md)，架构与证据分别见 [architecture.md](architecture.md) 和 [compatibility.md](compatibility.md)。

## R1 目标与交付范围

为 CLIProxyAPI（CPA）提供一个 WorkBuddy 动态库插件，通过 WorkBuddy 浏览器登录获得凭证，代理账号可用的模型请求。登录、凭证保存、启停和调度复用 CPA 的机制，适用于本机及容器部署。

| 项目 | 实施基线 |
|---|---|
| 插件 ID / 动态库名 | `cpa-workbuddy`；扩展名按平台为 `.dll`、`.so`、`.dylib` |
| provider key | `workbuddy` |
| 国内站点 | `https://copilot.tencent.com`；凭证 `site=workbuddy` |
| 国际站点 | `https://www.workbuddy.ai`；凭证 `site=workbuddy-ai` |
| 国内模型 ID | `wb/<上游模型 ID>` |
| 国际模型 ID | `wb-ai/<上游模型 ID>` |
| 登录方式 | WorkBuddy 浏览器登录；服务端轮询并由 CPA 保存凭证 |
| 账号数量 | 两站点均支持多个账号，以及同一用户的个人/企业身份 |
| 首版模型范围 | 账号 `/v3/config` 的 CLI 模型及企业 `custom:` 模型，涵盖其全部对话模型 |
| 首版请求能力 | 流式、非流式、多轮、工具调用、上游支持的图片输入和 reasoning |
| 国内 Claude 系列 | 使用 WorkBuddy 自身的 `/v1/messages`，纳入首版 |
| 其他对话模型 | 使用对应 WorkBuddy 站点的 `/v2/chat/completions` |
| 凭证管理 | CPA 的登录接口、凭证文件、列表、刷新、禁用及删除机制 |
| 模型发现失败 | 使用同一账号最近成功的模型快照；无快照则暂不注册可路由模型 |

“Claude”在本文中指 WorkBuddy 提供的模型系列。它不引入其他服务的登录或密钥；所有模型请求都发送到上述 WorkBuddy 站点。

### R1.1 范围边界

- 登录只使用浏览器流程；插件不读取 WorkBuddy 桌面文件，不导入或接收 API key。
- 管理体验复用 CPA；不交付独立管理页，不修改用户正在运行的桌面应用。
- CPA宿主与CPAMC管理前端必须保持未修改的官方源码和发行物；禁止修改其源码、交付或维护补丁，不以定制构建作为安装前提。可按所需公开能力提高最低兼容版本；版本范围必须依据实际验收，不固定为v7.3.15，也不把尚未验证的未来版本声明为兼容。
- 官方最新版本仍存在能力缺口时，先汇报本项目业务调整的具体影响，由用户决定后再实施；不得通过修改 CPA 补齐。
- 用量、积分、套餐、签到及仅免费模型筛选属于后续独立范围，不影响首版聊天验收。
- 国际目标为 `www.workbuddy.ai`。独立的 CodeBuddy 服务不是本项目目标。
- 本需求的“全部模型”指账号配置中的对话模型；不据此承诺图片生成、视频、语音或 embeddings 等其他 API。
- 保留工作树变更；只有用户明确指示才 commit、push 或发布。

### R1.2 已确定的设计取舍

1. 一个插件、一个 provider key；凭证的 `site` 决定站点。
2. 插件自管模型前缀，`AuthData.Prefix` 留空；隔离不依赖 CPA 的 `force-model-prefix` 配置。
3. 均衡仅发生于同站点且支持请求模型的凭证之间；调度策略由 CPA 管理。
4. 模型发现以账号成功快照为依据，静态目录不替代账号权限发现。
5. 首版包括 WorkBuddy 国内 Claude 的 Messages 路由及跨协议处理。
6. 参考包标注 MIT；项目采用 MIT，移植代码时保留所需版权及许可证声明。

## R2 核心不变量

### R2.1 站点与模型隔离

| 凭证站点 | 可注册模型 | 上游主机 |
|---|---|---|
| `workbuddy` | `wb/*` | `copilot.tencent.com` |
| `workbuddy-ai` | `wb-ai/*` | `www.workbuddy.ai` |

- `model.for_auth` 只返回当前凭证站点且属于该账号成功模型快照的 ID。
- `model.static` 可提供两站点静态目录用于元数据；不能让没有成功模型发现的账号获得整套静态模型的路由资格。静态注册对无凭证请求的实际影响须通过 CPA 集成测试核验。
- executor 使用 CPA 已解析的执行模型作为上游选择依据，校验其站点前缀后只剥离一层。无前缀、未知前缀及前缀与凭证站点冲突均返回明确客户端错误，且不请求上游。
- 原始 payload 可能保留客户端别名；不能仅因其模型字段与执行模型字面不同就拒绝合法别名。请求整形以后使用解析出的上游模型 ID。
- `AuthData.Prefix` 保持为空。`excluded_models` 及 CPA 别名映射的源模型使用带站点前缀的 ID。
- 响应中存在 `model` 字段时，按已解析的站点模型 ID 写回；保留 CPA 进行客户端格式转换所需的信息。
- 账号身份、模型快照、刷新协调及兼容处理缓存均包含站点和账号作用域，不跨账号复用。

### R2.2 凭证身份与存储

- 插件只解析自身拥有、类型与版本可识别的浏览器登录凭证；不能把任意含 `access_token` 的其他 provider 文件接管为 WorkBuddy。
- 设计带版本的持久化结构，包含 provider 标识、`site`、用户 ID、企业/租户作用域、展示名、access/refresh token、过期时间及必要模型快照信息。
- 稳定身份基于 `site + uid + enterprise/tenant scope`；同用户个人身份与企业身份分别保存，同一身份重新登录更新原记录。
- `AuthData.ID` 使用完整身份摘要，独立于展示名；`FileName` 使用可读账号名称和区分身份的短摘要，`Label` 保存账号展示名。规范文件名写入凭证的 `file_name`，解析、刷新和同身份重登保留；昵称变化更新Label，文件重命名经宿主管理接口明确迁移。三者与刷新保存目标必须指向同一逻辑记录，名称中不包含token。
- 凭证文件位置与写盘交给 CPA。插件不把本机绝对路径写成容器部署依赖，不直接写用户 auth 目录。
- 刷新、重新登录及快照更新必须保留宿主管理的手动禁用状态、优先级、代理和排除模型等设置。重新登录成功应清除旧凭证导致的认证错误，不能把“保留管理设置”误解为保留旧失效状态。
- 删除凭证立即移除凭证记录并阻断其实际调用；允许官方 Windows CPA 的全局模型目录暂时保留该凭证的独占模型，不能把目录残留当成仍可调度。部署记录此边界；需要立即清理目录时先禁用再删除，或重启宿主。此行为以目标官方版本实际验收为准。
- 访问 token、refresh token、登录 state 和完整账号响应不得进入插件日志、样本、测试快照或发布物；同时核查宿主请求日志的敏感头处理。
- 上游地址由 `site` 常量决定；不能直接信任凭证或客户端提供的任意 endpoint。企业/租户头与当前凭证作用域绑定。

## R3 功能与协议契约

### R3.1 浏览器登录与 CPA 集成

1. CPA 原生 OAuth 登录接口调用 `auth.login.start`；两个公开登录入口明确映射国内与国际站点。登录入口标识与持久化 provider 分离，凭证 provider 始终为 `workbuddy`。
2. 插件请求对应站点的 `POST /v2/plugin/auth/state?platform=...`，获取 state 和登录 URL。
3. 登录 URL 追加参考协议需要的 `version` 与随机 `loginSessionId`，校验 URL 的协议与目标域名。
4. 用户自行打开浏览器完成 WorkBuddy 登录；服务端轮询 `GET /v2/plugin/auth/token?state=...`。
5. 获取 token 后请求 `/v2/plugin/login/account`，必要时合并 `/v2/plugin/accounts`，确定所选个人或企业身份。
6. `auth.login.poll` 返回完整 AuthData；CPA 负责保存文件、注册凭证、返回管理列表。

约束与异常：

- 国内/国际入口均须可明确选择，不从 token 内容或任意 domain 猜测站点。入口映射到 `site=workbuddy` / `site=workbuddy-ai`；metadata 若显式携带 site，必须与入口一致。
- 登录状态隔离保存；验证并发登录、未知 state、过期、重复轮询和插件重启。过期后清理状态，重启后可明确重新发起登录。
- 参考轮询等待码为 token `11217`、account `12151`；等待与终止失败必须区分。参考等待窗口为 5 分钟，实际有效期与宿主约束共同决定。
- 从 WorkBuddy 登录页所选身份确定个人/企业作用域，不能任意切换成另一企业身份。
- 管理接口的鉴权复用 CPA；凭证保存成功后可在现有列表查看、刷新、禁用及删除。

### R3.2 刷新与失效处理

- `POST /v2/plugin/auth/token/refresh` 使用 `X-Refresh-Token`、`X-Auth-Refresh-Source: plugin` 和当前站点 domain；企业头遵循对应接口契约。
- 宿主定时刷新与执行期间刷新共享同一个协调入口。同账号同代 refresh token 单飞，结果保留 60 秒，避免并发重复消费。
- 自动刷新采用原版 `refresh_interval_seconds=300` 的五分钟周期调度，允许比仅在过期前五分钟执行一次更频繁地续期。上游绝对时间按毫秒、相对时间按秒解析，不依赖宿主保留插件返回的逐次 `NextRefreshAfter` 计划。
- 请求收到 401 时，优先检查该账号是否已有更新后的凭证；需要时刷新，再重发一次。刷新后再次拒绝必须终止，不能无限循环。
- 新凭证通过 `auth.refresh` 结果交给 CPA 原生 Manager 保存并安装，后续请求与模型发现采用宿主已安装的凭证。宿主保存失败时允许以 warning 日志显式告警并继续使用新内存凭证，不要求刷新 RPC 因此失败；未确认落盘时明确存在重启丢失风险。
- 暂时网络错误或刷新服务错误与明确凭证失效分别处理；旧 access token 尚有效时不因暂时故障宣告账号永久失效。
- 401、`invalid_grant`、`invalid_token` 等失败映射及 CPA 的账号状态、副作用需在目标宿主测试。插件不能仅因配置获取失败就标记账号失效。

#### 必须重新登录的凭证失效

这里指 WorkBuddy 已明确拒绝当前登录凭证，且刷新也无法恢复的认证失败。它与 access token 到期但可刷新、网络故障、模型无权限及额度不足分别处理。

- 判断依据包括明确的 refresh token 撤销/拒绝、`invalid_grant`，或按协议完成恢复后 access token 仍被明确判定无效。单次普通 401 或刷新超时不能直接证明永久失效。
- 刷新凭证被永久拒绝时，采用 CPA 原生需要重新登录的提示和拒绝刷新凭证记忆，避免反复消费同一个已拒绝的 refresh token。状态字段、文案及布局以目标官方 CPA/前端实际支持为准。
- 尚未到期且未被上游拒绝的 access token 可以继续用于推理，即使 refresh token 已被永久拒绝；access token 被实际拒绝或到期、且刷新无法恢复后，由原生生命周期阻断该凭证。
- 失效与用户手动禁用是两类状态，不通过冒充用户禁用、伪造过期时间或删除凭证来实现错误展示。
- 插件不得用模型快照扩大账号资格。重启后允许由官方 CPA 重新验证凭证并重建认证状态，不要求立即恢复上一进程的永久拒绝内存状态；文件存在本身不构成真实账号能力验收证据。
- 各入口均区分刷新凭证拒绝、访问凭证拒绝及临时故障；认证状态与调度遵循 CPA 原生生命周期，模型发现失败继续遵守账号模型资格规则。

宿主状态字段、刷新错误与调度的实际边界以所选官方版本的源码和运行验收为依据。公开接口仍不能满足的业务要求必须先汇报并由用户决定，不修改 CPA。

#### 同账号重新登录与原记录恢复

- “同账号”按 `site + uid + enterprise/tenant scope` 判断，不按昵称、邮箱展示名或 token 字符串判断。不同站点、个人与企业身份、不同企业身份各自保存。
- 原失效记录未删除时，重新登录同一身份应更新原来的稳定 ID/FileName 和凭证记录，列表仍只有一条对应记录；用户不需要先删除旧卡片。
- 成功保存并安装新凭证后，清除原凭证的认证失效标记、认证错误及相应模型认证冷却，更新刷新时间并重新获取模型列表。没有可用模型列表时仍遵循账号模型发现规则。
- 保留用户手动禁用、优先级、代理及排除模型等设置。原记录若被用户禁用，重新登录更新凭证后仍保持禁用；额度或其他非认证限制不能因为重新登录就被误判为已解除。
- 重新登录取消、超时、账号确认失败或保存失败，不删除旧记录，也不清除其已有失效状态或显示登录成功。
- 原凭证的在途请求、刷新及短时缓存必须与凭证代次绑定，不能在重新登录完成后把旧 token、旧失效判定或旧刷新结果写回，覆盖新状态。
- 验证新凭证的 token/过期时间按宿主可识别的契约映射；不能只把 token 藏在 StorageJSON 中，导致宿主无法识别凭证已变更。

稳定文件名只解决更新目标，不等于卡片状态和所有调度状态已经恢复。必须联合验收重新登录后的列表、模型注册、实际调度及重启恢复；对应宿主源码见 [兼容性记录](compatibility.md#认证失效与重新登录的宿主边界)。

### R3.3 模型发现与快照

- 使用当前浏览器凭证读取本站点 `GET /v3/config`。
- 解析 `agents` 中 `name=cli` 的模型 ID，再补充 `models` 中的企业 `custom:` 模型；保留上游 ID 的完整内容，包括 `:`、`|` 等字符。
- 模型按 ID 去重，不按展示名去重；展示名冲突可附加区分信息，不能合并不同上游模型。
- 解析输入上下文、最大输出、图片能力、reasoning levels/default effort 和价格来源；只声明 CPA ModelInfo 实际可表达的字段，不把积分倍率伪装成未经换算的货币价格。
- 国内 Messages 模型的 `max` effort 以路由能力为前提；国际 GLM 的图片能力按参考限制处理，模型元数据不能承诺会被上游丢弃的图片输入。
- 成功且结构有效的响应更新该账号进程内快照，保存成功时间和作用域。登录及原生刷新结果携带当前快照，由 CPA 与凭证一起持久化；普通模型发现不承诺每次立即落盘。重启后沿用最近一次已落盘快照，该快照可能早于最后一次普通发现。空模型列表与网络失败、格式损坏、缺少 CLI 配置分别判定，不能都解释为“用静态目录”。
- 临时发现失败：沿用同一账号最近成功的进程内快照，重启后采用最近持久化快照，并报告其时间与失败原因；没有快照时不注册可路由模型。不会回退到另一账号、另一企业或另一站点；明确访问凭证拒绝不授予模型资格，刷新凭证拒绝但 access token 仍可用时按原生生命周期处理。
- 重新登录、企业身份变化、凭证删除与插件重启分别验证快照更新、隔离、清理及恢复。宿主何时重新调用模型发现、如何从首次失败恢复，在集成阶段明确。

### R3.4 请求格式与路由

路由只根据已选凭证站点及已解析上游模型确定：

| 条件 | WorkBuddy 上游协议 |
|---|---|
| 国内站点，`claude-*` | `/v1/messages`，Anthropic Messages |
| 国内其他模型 | `/v2/chat/completions`，OpenAI Chat Completions |
| 国际所有对话模型 | `/v2/chat/completions`，OpenAI Chat Completions |

CPA 客户端协议与 WorkBuddy 上游协议是两回事。首版必须验证 OpenAI Chat、Responses、Claude Messages 及 CPA 支持转换的 Gemini 请求进入适当路由，再把结果转换回客户端格式；不能按客户端协议错误选择站点或模型。

- 实施前核对 CPA 的输入/输出格式声明与宿主翻译边界，确定原生 Messages 和 Chat 之间每一方向的转换归属。
- 国内 Claude 通过 OpenAI 客户端请求时仍须可用；Claude 客户端请求国际或国内非 Claude 模型时仍走 Chat。
- 转换必须保留文本、上游支持的图片、工具调用/结果、usage、停止原因及 reasoning 的可表达语义；不能以只声明两个 format 字符串当作转换完成。
- `executor.count_tokens` 和 `executor.http_request` 的支持范围在 ABI 核对时明确。参考记录 WorkBuddy `/v1/messages/count_tokens` 为 404；如宿主已有估算机制则复用其契约，否则返回明确不支持，不能伪造上游计数。

### R3.5 Chat 请求与响应

- 上游使用 `stream:true`，请求 JSON gzip；非流式客户端由插件聚合上游 SSE。
- 按站点与账号生成 Authorization、用户、domain、企业及租户头。
- 参考版本常量为 app `5.9.3`、CLI `2.165.0`；集中维护 UA、`X-IDE-*`、`X-Agent-*`、`X-Requested-With`、`X-Stainless-*` 等字段，10085 显式报版本兼容问题。
- 会话/轮次 ID 包含账号作用域；同一用户轮次的工具循环与重试保持 request ID 稳定，下一轮变化。优先使用宿主已有会话信息，再使用参考实现可证明的消息派生方式。
- 请求整形包含默认 system、`developer`、`max_completion_tokens`、历史 reasoning、`tool_choice`、默认 effort、工具 JSON Schema 修复及工具名映射。
- 默认 effort 服从调用方显式值；参考的低 token budget 例外需覆盖，避免短标题/分类请求把预算全部消耗在 reasoning。
- 工具名安全化必须处理碰撞，并在流式调用、聚合响应及历史记录中保持可逆映射，不能把不同原始工具名合成同一个工具。
- WorkBuddy AI 的 `extra_vars.growthEvent` 按参考行为生成，保留调用方可兼容的已有字段。
- SSE 解析不得依赖网络 chunk 边界；覆盖拆分 UTF-8、多行事件、空 delta、工具参数碎片、usage、结束事件及异常 EOF。
- 流式输出允许为模型 ID、工具名及协议规范化重写事件；验收目标是语义与事件顺序正确，不是字节原样透传。
- 非流式聚合包含 content、reasoning、tool_calls、finish_reason 和 usage；上游中途失败不得返回伪成功的完整回答。

### R3.6 国内 Claude 的 Messages 请求与响应

- 仍使用同一份国内 WorkBuddy 浏览器凭证、企业头和会话归属。
- 原生请求保留 Messages 的 system、content blocks、tool_use/tool_result、thinking 与签名语义，避免套用 Chat 专属整形。
- effort 通过 Messages 协议字段传递；`max` 仅对支持的模型声明。
- 参考行为会处理无签名 thinking 与签名不匹配错误 11159；保留合法签名，必要的纠正只能发生在尚未向客户端发送回答之前。
- 覆盖流式与非流式、工具循环、客户端协议转换、模型前缀回写、usage 与停止原因转换。
- 不因为 Messages 请求失败就自动改投另一站点或另一协议，防止改变模型语义与重复执行。

### R3.7 重试、取消与资源生命周期

| 场景 | 行为边界 |
|---|---|
| 401 | 同账号读取更新状态/刷新后重试一次 |
| 11128 | 按参考顺序做逗号纠正、必要时移动 system；按作用域记忆成功策略 |
| 11153 | 符合 tool 结果后接 user 的形状时插入空 assistant，并记忆适用模型 |
| 11159 | Messages thinking 签名纠正，限定次数 |
| 11140 / 14018 / 10085 | 明确反馈风控、额度或版本问题，保留上游错误信息 |
| 429 / 5xx / 超时 | 映射宿主重试语义及 Retry-After，插件不额外叠加无界重试 |
| 已向客户端发出回答事件 | 不再重放整次请求；流内失败按宿主协议终止 |
| 客户端取消/超时 | 取消上游读取、关闭上下游流并释放请求资源 |

- 明确每条纠正规则的次数与组合总上限；重试沿用该轮会话归属。
- 内容安全过滤保留明确的停止语义；首版不依赖隐藏拒绝文本来触发另一账号重试。
- host callback ID、C buffer、宿主上游 stream ID 和下游 stream ID 必须有明确所有权与释放路径。
- 有界读取与缓存覆盖请求体、错误体、SSE 单事件、非流式聚合及队列；具体限制结合目标宿主配置确定并记录，不能靠无限缓冲实现流式。
- shutdown 时停止接收新任务，取消并等待在途任务，释放缓存及回调资源；释放之后不能再调用宿主。

| 领域 | 必须覆盖的消费者可见行为 | 验证方式 |

| 调度 | 两站点各至少两凭证、模型排除、别名、禁用/删除 | 记录实际命中 auth ID 的 CPA 集成 |
| Chat | gzip、内容/reasoning/工具、图片限制、SSE 分片、非流式 usage | 假上游协议测试 + 账号 smoke |
| Messages | 国内 Claude、签名、max、工具循环、停止原因 | Messages 样本 + 账号 smoke |
| 跨协议 | OpenAI Chat/Responses、Claude、Gemini 的宿主转换边界 | 有代表性的双向转换场景 |
| 稳定性 | 指定错误码、重试上限、流后失败、客户端取消 | 故障注入与资源关闭断言 |
| 容器/发布 | 持久卷恢复、代理、CGO 依赖、插件文件名 | 隔离部署 smoke + 平台 CI |

- 假上游只模拟协议与错误，不替换业务逻辑。新增永久测试针对并发、状态机、流分片、协议转换等不确定边界，不断言源代码措辞或重复实现细节。
- 每片任务运行覆盖变更的最窄检查；切片结束运行适用的 Go 测试、静态检查及 CGO 构建。出现失败先解决，再进入下一切片。
- 非平凡代码变更完成后，按仓库规则先完成索引同步，再执行 `post-impl` 七维审查，修复后重跑受影响检查，并在交付回复中列明结论。
- 验证不启动可见窗口、不操作桌面。需要浏览器 DOM 验证时只使用隔离 headless；真实登录与主观界面体验交由用户。
- 每个验收结果记录为“通过 / 失败 / 未验证”，附运行环境和证据；网络可达不能代替登录成功，构建成功不能代替宿主加载成功。

## 附录 A：CPA 凭证与模型机制问答

保留相关问题，供理解实现约束；本附录解释现行方案，不增加实施范围。源码对应表集中在 [兼容性记录](compatibility.md#五项问答的源码对应)。

**1）登录后会不会出现凭证卡片？**

浏览器登录轮询成功后，插件返回 AuthData，CPA 保存 auth 文件并注册凭证。管理端通过 `/v0/management/auth-files` 取得记录；具体卡片布局由目标管理前端决定。

- 保存登录记录：`../.cpa-upstream-src/internal/api/handlers/management/auth_files_provider_oauth.go:1025`。
- 构造凭证列表项：`../.cpa-upstream-src/internal/api/handlers/management/auth_files.go:637`，字段从 `:655` 起。
- `Label` 使用账号名、站点与必要企业信息，使同名用户的不同身份可以区分。

**2）没有卡片，CPA 能不能拿到模型？**

模型获取与前端布局独立。宿主调用 `ModelsForAuth`，将模型以 auth.ID 注册到模型表；能否路由取决于有效凭证与其模型注册结果。首次发现失败且没有成功快照的账号不获得静态模型路由资格。

- 模型获取入口：`../.cpa-upstream-src/sdk/cliproxy/service_models.go:67`、`service_executors.go:498`。
- 以 auth.ID 注册：`../.cpa-upstream-src/sdk/cliproxy/service_executors.go:428`、`:454`。

**3）请求会不会派发到“对应凭证”的模型上？**

CPA 按每张凭证支持的模型筛选候选，再应用自身调度策略。某模型只在账号 A 的成功列表中时，只有 A 可被选中；多个账号都支持它时可在同站点候选之间均衡，不保证固定账号。

- 支持性检查：`../.cpa-upstream-src/sdk/cliproxy/auth/conductor_selection.go:985`，通过 `ClientSupportsModel(auth.ID, routeModel)` 判断。
- 候选过滤：同文件 `:1756`。
- 静态目录无法证明账号权限，因此账号模型失败时使用本账号快照，无快照则不注册。

**4）一个插件能管理多个国内账号 + 多个国际账号吗？**

可以。每次浏览器登录产生对应身份的 AuthData；唯一且稳定的 ID/FileName 使不同站点、用户及企业身份分别落盘。同身份重新登录更新其记录。

- 官方 `sdk/pluginapi.AuthData` 分别提供ID、FileName和Label；宿主保留显式ID，管理列表的name取FileName，缺少FileName时才取ID。位置为固定官方 `internal/pluginhost/auth_provider.go:1307-1324` 与 `internal/api/handlers/management/auth_files.go:667-678`。
- 文件路径解析：`../.cpa-upstream-src/sdk/auth/filestore.go:411-440`。
- 文件名示意为 `WorkBuddy AI · 张三-<短身份摘要>.json`；完整摘要仍在AuthData.ID，包含站点、用户及企业/租户作用域。既有或导入的源文件名由宿主提供并写入file_name，迁移通过管理接口完成。

**5）CPA 的全局模型表按模型 ID 合并是什么意思？**

CPA 的模型注册分两层：每凭证层保存 `RegisterClient(auth.ID, "workbuddy", models)` 的模型列表与元数据；全局层按 modelID 汇总 client 数量、provider 及一份公开 Info。

- 同名模型再次注册时更新计数与公开 Info：`../.cpa-upstream-src/internal/registry/model_registry.go:670-675`。
- 对外模型列表按 ID 汇总：同文件 `:1347-1364`。
- 路由资格仍检查每凭证支持列表：同文件 `:1183`。

国内的 `wb/glm-5.3` 与国际的 `wb-ai/glm-5.3` 是两个不同 ID，分别属于各自站点的凭证列表。同站点多账号的同 ID 模型可在全局层合并，但这种合并不证明各账号的配额或全部元数据相同。

前缀由插件生成，`AuthData.Prefix` 留空；执行前校验站点并剥离前缀，响应写回站点模型 ID。隔离同时依赖模型注册与 executor 校验，通过双站点多凭证测试验收。
